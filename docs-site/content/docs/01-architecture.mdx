## 整体架构

TraceHound 采用 **"数据层 → 工具层 → 诊断层 → 交互层"** 四层架构。每层职责清晰，层间通过 MCP 协议通信。

```
┌──────────────────────────────────────────────────────────────────┐
│                       交互层 (Diagnostic Cockpit)                 │
│   Web 诊断面板：排查步骤可视化 | 调用链展示 | 证据面板 | 因果链    │
│   SRE 实时观察 + 质疑纠正 → Agent 根据反馈纠偏                     │
└──────────────────────────────┬───────────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────────┐
│                       诊断层 (Agent + Skill)                      │
│  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐   │
│  │ RT-Spike Skill  │  │ CPU-Spike Skill │  │ Error-Burst     │   │
│  │ 服务延迟诊断     │  │ CPU 飙高诊断     │  │ Skill 报错诊断   │   │
│  └─────────────────┘  └─────────────────┘  └─────────────────┘   │
│  告警路由 → Skill 匹配 → 多步诊断 → 因果链输出 → 经验沉淀        │
└──────────────────────────────┬───────────────────────────────────┘
                               │ MCP 协议
┌──────────────────────────────▼───────────────────────────────────┐
│                       工具层 (6 大子系统)                          │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐            │
│  │ Trace    │ │ 日志     │ │ 主机 &   │ │ 中间件   │            │
│  │ Viewer   │ │ 平台     │ │ 进程监控  │ │ 监控     │            │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘            │
│  ┌──────────┐ ┌──────────┐                                       │
│  │ 变更管控  │ │ 知识经验  │                                       │
│  │ 平台     │ │ 库       │                                       │
│  └──────────┘ └──────────┘                                       │
└──────────────────────────────────────────────────────────────────┘
```

## 数据流：从告警到诊断

```
1. 告警触发（Prometheus / Grafana / PagerDuty）
   │  Alert Payload: { service, metric, severity, time, cluster }
   │
2. Skill 路由
   │  根据 metric + service_type 匹配对应的诊断 Skill
   │
3. Agent 启动诊断
   │  ├── Step 1: 采集上下文（调用 MCP 工具拉数据）
   │  ├── Step 2: 分析 + 假设验证
   │  ├── Step 3: 交叉验证 + 排除干扰
   │  └── Step 4: 输出因果链 + 置信度
   │
4. 结果呈现
   │  ├── 诊断面板实时展示排查进度
   │  ├── SRE 可质疑/纠偏任何步骤
   │  └── 确认后沉淀为病例
   │
5. 经验闭环
   └── 结构化保存 → 下次类似告警自动检索匹配
```

## 核心设计决策

### 1. 为什么不做实时数据监听？

传统监控系统（Prometheus 规则引擎）在**毫秒级异常检测**上已极度成熟。让 LLM Agent 去监听海量实时数据流既不经济也不准确。TraceHound 选择**告警回调驱动**——只在告警触发后才介入，把 LLM 的推理能力用在最有价值的**关联分析 + 因果推断**环节。

### 2. 为什么按场景拆分 Skill？

不同故障场景的诊断逻辑、数据依赖、推理链路完全不同：

- RT 飙升需要 Trace + 慢查询 + GC
- CPU 飙高需要 perf + 线程 dump + top
- 报错突增需要日志聚类 + 变更关联

强行用一个 Agent 覆盖所有场景会导致"什么都会、什么都不精"。拆分 Skill 后每个诊断流程可独立深度优化。

### 3. 为什么经验闭环是关键？

没有经验沉淀的 Agent，每次诊断都是"冷启动"。有了结构化病例库 + 检索机制，Agent 可以：

- **检索相似病例** — "这个服务 2 周前出现过类似 RT 飙升，根因是 DB 连接池耗尽"
- **复用诊断路径** — 已验证的排查步骤直接走，不需要从头推理
- **持续优化** — 反馈纠偏 → 更新已知故障模式 → 越来越准
